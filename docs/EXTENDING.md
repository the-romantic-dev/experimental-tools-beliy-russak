# Свои компоненты в пайплайне без правки его кода

**Это механика `aic_pipeline`, а не библиотеки `aic`.** Реестры и
`aic_plugins.py` существуют потому, что пайплайн собирает модель, лосс и
аугментации по строкам из YAML: чтобы имя из конфига превратилось в функцию,
нужен реестр. Библиотека ничего по имени не собирает и расширяется обычным
способом — своими функциями вокруг её объектов, см.
[aic-quickstart.md](aic-quickstart.md).

Пайплайн один на команду, а гипотезы у каждого свои. Чтобы новый лосс или
пресет аугментаций не означал pull request и новую версию у всех, шесть точек
конфига открыты наружу: кладёшь `aic_plugins.py` в корень своего воркспейса и
пишешь в конфиге своё имя.

## Сначала проверь — может, плагин не нужен

Большая часть перебора уже открыта, и городить ради неё файл не надо:

* **Архитектура и энкодер.** `model.arch` уходит прямо в `smp.create_model`,
  `model.encoder` — в timm через префикс `tu-`. Любая архитектура из smp, любой
  энкодер из timm работают как есть.
* **Любые числа.** lr, batch size, размер входа, число эпох, веса компонент
  лосса, alpha/beta/gamma, доли негативов и мелких масок, сетки калибровки.
* **Структура конфигов.** `_base_` разрешается относительно самого файла, так
  что своя иерархия в своём `configs/` работает без всяких настроек. И
  `-s любой.новый.ключ=значение` создаёт ключ, которого в базе не было.

Плагин нужен тогда, когда появляется **новый вид** сущности: лосс, которого нет
в списке, свой оптимизатор, свой набор аугментаций.

## Быстрый старт

```bash
cp docs/aic_plugins.example.py ~/моя-папка/aic_plugins.py
```

Файл кладётся в корень воркспейса — туда же, где лежит `configs/`. Внутри:

```python
import torch
from aic_pipeline import register_loss


@register_loss("soft_iou")
def soft_iou(logits, targets, *, smooth=1.0):
    probs = torch.sigmoid(logits).flatten(1)
    targets = targets.flatten(1)
    intersection = (probs * targets).sum(dim=1)
    union = probs.sum(dim=1) + targets.sum(dim=1) - intersection
    return 1.0 - (intersection + smooth) / (union + smooth)   # тензор (B,)
```

В конфиге — обычное имя, никакой новой грамматики:

```yaml
loss:
  seg: {bce: 1.0, soft_iou: 1.0}
  soft_iou: {smooth: 1.0}       # приедет в **params
```

Проверить, что библиотека увидела:

```bash
aic registry
```

Именованные параметры компоненты берутся из секции `<ключ>.<имя>` — ровно тем
же способом, каким уже настраиваются встроенные `tversky` и `focal`.

## Куда библиотека смотрит

Три способа, по возрастанию формальности:

| способ | когда |
|---|---|
| `<воркспейс>/aic_plugins.py` | по умолчанию: свои гипотезы, только для себя |
| ключ `plugins: [пакет.модуль]` в конфиге | общие компоненты команды в устанавливаемом пакете |
| `aic_pipeline.load_plugins(["пакет.модуль"])` | из ноутбука или своего скрипта |

Загрузка ленивая и одноразовая: её запускает первое обращение к любому реестру.
Поэтому неважно, зашёл ты через `aic train`, через `build_loss` напрямую или из
ноутбука — плагины будут на месте.

Воркспейс определяется как обычно: `AIC_WORKSPACE`, иначе ближайшая вверх папка
с `configs/`. Где он сейчас и подключён ли файл — печатает `aic env`.

## Справочник: шесть точек расширения

| декоратор | ключ конфига | функция получает | должна вернуть |
|---|---|---|---|
| `register_loss` | `loss.seg.<имя>` | `(logits, targets, **params)` | тензор `(B,)` |
| `register_aug` | `data.aug` | `()` | список пиксельных операций |
| `register_val_mode` | `data.val_mode` | `(size)` | список операций геометрии |
| `register_optimizer` | `train.optimizer` | `(param_groups, cfg_train)` | `Optimizer` |
| `register_scheduler` | `train.scheduler` | `(optimizer, cfg_train, total_steps, warmup_steps)` | scheduler или `None` |
| `register_backend` | `model.backend` | `(cfg_model)` | `nn.Module` |

Каждый декоратор работает и как декоратор, и как обычный вызов:
`register_loss("имя", функция)`.

### Куда класть параметры своей компоненты

В секцию, названную её же именем, рядом с ключом выбора:

```yaml
loss:
  seg: {bce: 1.0, soft_iou: 1.0}
  soft_iou: {smooth: 1.0}        # параметры компоненты лосса
train:
  scheduler: step
  step: {gamma: 0.3}             # параметры планировщика
data:
  aug: forensic
  forensic: {quality: 40}        # параметры пресета
```

Так же устроены встроенные `tversky` и `focal`, так что правило не новое.

У него есть вторая причина. Конфиг проверяется на опечатки, и ключ россыпью
(`train.step_gamma`) неотличим от описки — на него будет предупреждение.
Секцию с именем выбранной компоненты проверка узнаёт по значению
`train.scheduler` и внутрь не смотрит.

### `register_loss`

**Возвращай значение на каждый кадр — тензор `(B,)`, а не скаляр.** Это не
придирка: при включённом профиле по площади (`loss.area`) библиотека взвешивает
кадры по отдельности — мелким маскам даётся другой состав лосса и другой вес.
Скаляр это сломает молча.

Параметры приезжают из `loss.<имя>`. Исторические формы записи тоже работают:
`bce` берёт `loss.pos_weight`, `dice` и `tversky` — `loss.dice_smooth`.

### `register_aug`

Только **пиксельная** часть аугментаций. Геометрия (`RandomResizedCrop`, флипы,
повороты на 90°) и нормализация остаются за библиотекой: они завязаны на
`data.size` и на то, как маска потом возвращается в исходное разрешение.

Порядок в итоговом `Compose`: геометрия → твои операции → `Normalize` →
`ToTensorV2`.

### `register_val_mode`

Геометрия валидации и инференса. Учти: `inference.py` умеет возвращать маску в
исходное разрешение только для `resize` и `pad`. Третью геометрию придётся
научить и его — иначе сабмит соберётся с неправильными масками.

### `register_optimizer`

`param_groups` приезжают готовыми: библиотека уже разложила параметры на
энкодер/декодер × decay/no-decay и проставила каждой группе свой `lr`. Это самая
неочевидная часть, и переписывать её каждому не нужно — твоё дело только сам
оптимизатор.

### `register_scheduler`

`total_steps` и `warmup_steps` библиотека считает сама: только ей известны и
длина эпохи, и накопление градиента. Планировщик шагает по **шагам оптимизатора**,
а не по эпохам.

### `register_backend`

Единственное жёсткое требование — форма выхода:

```python
{"logits": (B, 1, H, W), "cls_logits": (B, 1)}
```

`H` и `W` — как на входе. `cls_logits` — «в кадре есть манипуляция», до сигмоиды;
по ней на инференсе целиком обнуляются маски чистых кадров, и это главный рычаг
против `FPR_neg`. Наследовать `SegModel` не обязательно.

## Когда не работает

**Первым делом — `aic registry`.** Он показывает все шесть реестров и откуда что
взялось:

```
loss
  сигнатура: fn(logits, targets, **params) -> тензор (B,), значение на каждый кадр
  встроенные:          bce, dice, focal, tversky
  aic_plugins:         soft_iou
```

Если твоей компоненты в списке нет — библиотека не нашла файл. Проверь `aic env`:
он печатает путь к воркспейсу и к `aic_plugins.py`, и подключён тот или нет.

**Опечатка в имени** ловится при сборке, а не на первом шаге обучения:

```
компонента лосса: нет варианта 'sof_iou'
  встроенные:          bce, dice, focal, tversky
  aic_plugins:         soft_iou
  похоже на 'soft_iou'?
  как добавить свою: @register_loss('sof_iou') в aic_plugins.py, сигнатура ...
```

**Плагин упал при импорте** — ошибка назовёт файл и причину; никакого «тихо не
загрузилось» не будет.

## Правила общежития

**Имена не переиспользуются.** Регистрация под занятым именем падает с ошибкой,
где написано, чей это модуль. Перебить встроенное можно только явно:

```python
@register_loss("dice", override=True)
```

Без этого чужой плагин молча подменил бы `dice`, и разбираться в расхождении
метрик пришлось бы долго.

**Общие компоненты — в пакет, а не копипастой.** Если наработка пригодилась
двоим, заводите отдельный маленький пакет и подключайте ключом `plugins:` в
общем `_base.yaml`. Два разошедшихся `aic_plugins.py` с одинаковыми именами и
разной математикой — ровно тот случай, ради которого затевался реестр.

**Прижилось — присылай в библиотеку.** Встроенные компоненты зарегистрированы
тем же самым декоратором (см. `losses.py`, `transforms.py`, `engine.py`), так
что переезд плагина внутрь — это перенос функции и тест.

**`aic_plugins.py` из репозитория не коммитится.** Это твой личный файл; в
репозитории лежит только `docs/aic_plugins.example.py` как образец.

## Что расширить нельзя

`model.stream` (SRM/Bayar-остаток) и `model.fuse` остаются закрытыми: они вшиты
в пирамиду энкодера, и реестр там протёк бы внутренностями наружу. Нужен свой
низкоуровневый фильтр — регистрируй целиком `backend`.

`data.source` (`raw`/`cache`) тоже закрыт: он завязан на раскладку файлов,
которую делает `aic precache`.

Метрика AIC не расширяется намеренно — она задана условием задачи, и подменять
её означало бы мерить не то, что оценивают.
